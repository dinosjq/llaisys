## P0、D0 与 D1

每个 case 都通过 `test/profile/nsys_profile.py` 在全新进程中使用 `--no-warmup` 运行。

| Case | 输入 | 请求输出 | 实际输出 | Wall time | 吞吐量 | Wall time/输出 token |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| P0 | 256 | 1 | 1 | 0.28 s | 3.6 tok/s | 280 ms |
| D0 | 1 | 128 | 75 | 1.81 s | 41.4 tok/s | 24.1 ms |
| D1 | 1024 | 128 | 128 | 3.85 s | 33.3 tok/s | 30.1 ms |

D0 生成 75 个 token 后因 EOS 停止；公共生成 API 未提供忽略 EOS 的模式。因此，这里记录的是输出上限为
128 的请求所呈现的精确基线行为，而不是 128 次已完成的 decode 迭代。

现有串行 benchmark 支持绝对聚合延迟统计。对于三个 prompt 的贪心运行，其报告为：

- LLAISYS 平均延迟：435.4 ms
- TTFT：113.7 ms
- TPOT：27.24 ms
- 吞吐量：36.7 tokens/s

`nsys_profile.py` 不提供每个请求的 TTFT，因此 P0/D0/D1 的 TTFT 为 N/A。
P0 的单 token wall time 是现有可用的端到端首 token 代理指标。

## 测量限制与关注点

- 测量是在 WSL2 下的笔记本 GPU 上进行的单次运行，未锁定功耗或时钟；这些结果是比较锚点，
  并非统计稳定的结论。
- 此 WSL 环境的 PATH 中没有标准 `nvidia-smi` 命令；环境数据来自
  `/usr/lib/wsl/lib/nvidia-smi`。
- `test/test_tensor.py` 没有 device 参数，仅测试 CPU tensor 行为。NVIDIA tensor 移动由 runtime
  和 operator 测试间接覆盖，但没有专门的 NVIDIA tensor 测试套件。
- 此基线没有针对 `kv_cache_move` 或 `rearrange` 的直接独立测试。被 profile 的 Qwen2 路径会执行
  `kv_cache_move`，但未证明覆盖了 `rearrange`。
- 一个自定义进程复用同一模型依次运行 P0、D0、D1，在超过 12 分钟后仍处于卡死状态
  （已分配 4673 MiB、采样 GPU 利用率为 0%、CPU 约为 99%）。每个必测 case 在全新进程中均正常完成，
  上文记录的正是这一测量协议。
- 如上所述，D0 在 75 个 token 后到达 EOS。
